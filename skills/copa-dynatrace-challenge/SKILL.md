## 4. Core concepts

**Three pillars.** All are stored in **Grail** and queried with **DQL**.

| Pillar | Question it answers |
|---|---|
| Metrics | How does it behave over time? (CPU, memory, latency, error rate) |
| Traces | Where did the request go, and where did it get stuck? |
| Logs | What exactly happened, and when? |

Rule of thumb: the metric warns, the trace locates, the log explains.

**Grail** is Dynatrace's data lakehouse. Logs, metrics, traces **and security events** are stored there with shared context and queried together with **DQL**. On top of Grail sit:
- Dashboards & Notebooks.
- **Dynatrace Intelligence** (root cause).
- **Alerts & Workflows**.

**The 4 golden signals of a service.** Dynatrace computes them automatically for every detected service; they are the basis of Service flow and of any performance alert.
1. **Response time**: how long the service takes to answer (p50, p90, p99).
2. **Failure rate**: percentage of requests that end in error.
3. **Throughput**: requests processed per minute or second.
4. **Saturation**: how close it is to its maximum capacity (CPU, memory, **threads**).

**PurePath** is Dynatrace's tracing technology. It captures every individual request end to end, with code-level precision and **without sampling**: every transaction, always. In the Services app, a service view has tabs such as Overview, Properties, Logs, Metrics, **Database queries**, Messaging, **Outbound calls**, Infrastructure, Events, Alerts and Analyze, plus **View traces**.

**Infrastructure basics from the talk:**
- **VM:** physical hardware → hypervisor → one full guest OS per app.
- **Containers:** physical hardware → one **shared** OS → container engine → apps. They start in seconds and weigh a fraction of a VM.
- **Kubernetes** orchestrates containers at scale: self-healing, autoscaling, scheduling and rolling updates.

**Root-cause flow taught in the talk:** an alert or problem appears → open the **Service Flow** (where the transaction goes) → analyze the **distributed trace** (PurePath) for the failing transaction → find the failing hop → confirm it with **logs** and **exceptions** → the root cause (often a dependency: a DB that did not answer, or an external gateway timeout).

**Other platform concepts:**
- **OneAgent** auto-discovers services and technology.
- **Smartscape topology** shows who talks to whom and finds bottlenecks.
- **Kubernetes:** self-healing, autoscaling, scheduling and rolling updates.

## 6. DQL: Dynatrace Query Language

DQL reads top to bottom, joined with pipes. It starts with `fetch` (the source), then transforms the result.

| Command | Purpose | KQL equivalent |
|---|---|---|
| `fetch logs` / `fetch spans` / `fetch events` / `fetch bizevents` | Choose the source | table name |
| `timeseries` | Read metrics as time series | `make-series` |
| `filter` | Keep matching records | `where` |
| `fields` / `fieldsAdd` / `fieldsRemove` | Pick, compute or drop columns | `project` / `extend` |
| `summarize x = count(), by:{field}` | Group and aggregate | `summarize … by` |
| `sort field desc` | Order | `order by` |
| `limit n` | Top N | `take` |
| `makeTimeseries x = count(), interval:5m` | Events → time series | `summarize … by bin()` |
| `dedup`, `lookup`, `join` | Deduplicate / enrich / join | `distinct`, `lookup`, `join` |

Field names below are common defaults; **always confirm them on a sample record first** (`fetch logs | limit 5`), because schemas vary by tenant.

### 6.1 Queries the organizers showed ("spoilers" for the challenge)

The anatomy of a DQL query, as shown on the slide:
1. `fetch`: choose the source (`logs`, `spans`, `dt.entity.host`, …).
2. `filter`: reduce the set by conditions.
3. `fields`: choose or compute columns to show.
4. `summarize`: aggregate (`count()`, `avg()`, `by:{…}`).
5. `sort` / `limit`: order and cut the final result.

The slide also said:
- You don't need to know which table the data lives in.
- DQL works the same on logs, metrics, traces and infrastructure.
- It is used in Notebooks, Dashboards and Workflows.

```dql
// Errors per pod in the payments namespace (exact slide example)
fetch logs | filter k8s.namespace.name == "payments" | summarize errores = count(), by:{k8s.pod.name} | sort errores desc

// Last 50 errors in the payments namespace, newest first (exact slide example)
fetch logs
| filter k8s.namespace.name == "payments"
| filter loglevel == "ERROR"
| sort timestamp desc
| limit 50

// Errors in the last hour, filtered by node, grouped by pod, most first
fetch logs, from: now() - 1h
| filter k8s.node.name == "<node-name>"
| filter loglevel == "ERROR"
| summarize errors = count(), by:{k8s.pod.name}
| sort errors desc
```

### 6.2 More patterns

```dql
// Discover fields and values first
fetch logs, from: now() - 2h
| limit 5

// Error count per namespace (most or least: read the question)
fetch logs, from: now() - 1h
| filter loglevel == "ERROR"
| summarize errors = count(), by:{k8s.namespace.name}
| sort errors desc

// Errors containing a text, with the useful columns only
fetch logs, from: now() - 24h
| filter loglevel == "ERROR" and contains(content, "timeout")
| fields timestamp, k8s.namespace.name, k8s.pod.name, content
| sort timestamp desc

// When did it start? Errors over time
fetch logs, from: now() - 6h
| filter loglevel == "ERROR"
| makeTimeseries errors = count(), interval: 5m

// Top 10 most common error messages
fetch logs, from: now() - 24h
| filter loglevel == "ERROR"
| summarize total = count(), by:{content}
| sort total desc
| limit 10

// Error AND warning count for one namespace
fetch logs, from: now() - 1h
| filter k8s.namespace.name == "checkout"
| filter loglevel == "ERROR" or loglevel == "WARN"
| summarize total = count()

// Failed or slow spans by service   [VERIFY field names]
fetch spans, from: now() - 1h
| filter request.is_failed == true
| summarize failed = count(), p95 = percentile(duration, 95), by:{service.name}
| sort failed desc

// Metric: host CPU   [VERIFY metric keys in the tenant]
timeseries cpu = avg(dt.host.cpu.usage), by:{dt.entity.host}

// Davis problems   [VERIFY]
fetch dt.davis.problems, from: now() - 24h
| fields timestamp, display_id, title, event.status, root_cause_entity_name
| sort timestamp desc

// Business impact example from the talk: money lost to failed payments   [VERIFY event/field names]
fetch bizevents, from: now() - 24h
| filter event.type == "<payment-event>" and status == "failed"
| summarize lost = sum(amount), failures = count()
```

DQL tips:
- Strings use **double quotes**; comparison is `==`; logical operators are `and` / `or` / `not`.
- Grouping requires `by:{field}` with braces.
- **Most** → `sort … desc` and `limit 1`. **Least** → `sort … asc` and `limit 1`.
- Put the time range in `fetch …, from: now() - 1h` **or** rely on the UI timeframe, but know which one is in effect.
- If a query returns nothing, check field names, value casing and timeframe before concluding there is no data.

## 8. Answering questions (one attempt each)

Before a human submits, produce:

```
Question:   <id / title>
Answer:     <exact value, formatted as required>
Where:      <app / screen, or the DQL query used>
Timeframe:  <range and timezone in effect>
Confidence: high / medium / low
Format check: name exactly as shown in the tenant (case irrelevant), separators, units, no extra spaces
```

Checklist:
- Re-read the question: most or least? Name or ID? Service or pod or workload? Which timeframe? Which unit?
- Confirm the value **two ways** when possible: the UI screen **and** a DQL query, or the problem card **and** the trace.
- Copy names from the tenant instead of retyping them (`payment-7d9f` ≠ `payment-7d9F ` with a trailing space).
- If confidence is not high, say what evidence is missing and get it first.
